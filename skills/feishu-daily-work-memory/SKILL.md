# 飞书每日工作记忆

把飞书作为事实源，使用官方 lark-cli 和已安装的 lark-* Skills 完成读取与写入。不要建立本地聊天库，不复制完整聊天正文，不把推测写成事实。

## 执行流程

1. 确认事件包含 `intent: daily_work_memory`、合法的 `target_date`，以及配置中的 `daily_memory.folder_token`。
2. 按主体用户时区计算目标日的开始与结束边界。当前时区为 `Asia/Shanghai` 时，使用目标日 `00:00:00+08:00` 到次日 `00:00:00+08:00`。
3. 按需读取官方 `lark-im`、`lark-task`、`lark-calendar`、`lark-drive`、`lark-doc` Skills 后生成读取命令。身份由运行时固定为 user，不在 argv 中写 `--as`。
4. 等待真实 `execution_feedback`，再归并事实、决定、承诺、任务、日程、风险和次日重点。
5. 每次都先在配置文件夹内搜索精确标题 `YYYY-MM-DD <principal.name>每日工作记忆`，其中 `<principal.name>` 必须替换为配置中的主体用户名称：
   - 找到一份时，更新这份文档；
   - 没找到时，创建新文档；
   - 找到多份时，更新最近的一份并把重复文档列为数据缺口，不再新建。
   - 只要精确标题搜索返回一份或多份结果，就禁止调用 `docs +create`；同一日期只更新原文档。
6. 第二轮必须执行文档写入，并且只使用第一轮已经返回的成功事实，不得只返回文字说明而不写文档。除精确标题搜索外，其他数据源失败不在本次运行重试，直接把失败类型和可能遗漏范围写入数据缺口，避免在纠正结果返回前先写出未经验证的结论。第三轮必须对刚写入的同一 token 执行 `docs +fetch`；只有读回内容除标题外仍有正文，且包含“来源引用与数据缺口”时，才算生成成功。
7. 等待写后读取结果，再在决策结果中返回文档链接、最多三项次日优先事项和任何数据缺口；本地定时运行不额外发送 Bot 或用户聊天消息。写后读回失败或正文为空时必须报告失败，不能把命令退出成功等同于日报成功。

## 官方读取能力

第一轮必须一次性发出五条事实读取命令完成事实收集，不要把这些读取拆到多个轮次。精确标题搜索失败时整次失败关闭；其他读取失败时直接记录为数据缺口，不在本次运行纠正：

- 聊天：`im +messages-search --start <开始> --end <结束> --page-size 50 --page-all --page-limit 10 --no-reactions`。无关键词时直接省略 `--query`，不要生成空字符串参数。汇总主体用户账号可见的群聊和私聊；保留工作群内审批、任务等 Bot 产生的业务事实，过滤纯通知噪声，不为 Bot 私聊建设独立补读链路。
- 未完成任务：`task +get-my-tasks --complete=false --page-all --page-limit 5`。重点提取逾期、目标日到期、等待他人和影响次日的事项。
- 目标日发生变化的相关任务：把目标日开始时间换算为微秒游标，使用 `task +get-related-tasks --page-token <目标日开始微秒> --page-limit 5` 读取；保留已完成任务，不要与 `--page-all` 同时使用。
- 日程：`calendar +agenda --start <目标日> --end <次日>`。
- 当日文档：`drive +search --query "<精确标题>" --folder-tokens <folder_token> --doc-types docx --only-title`。

任何单个读取失败都不能阻止生成日报。使用成功返回的事实继续生成，并把失败的数据源、官方错误类型和可能遗漏范围写入“来源引用与数据缺口”。

精确标题搜索是写入前置条件：该命令失败或返回 `has_more: true` 时，本次运行失败关闭，不创建也不覆盖文档。聊天、任务或日程等其他数据源失败时，不在同一次日报内重试；使用成功结果继续生成，并在“来源引用与数据缺口”中记录官方错误类型和可能遗漏范围，始终保持三轮执行反馈。

如果所有成功读取的数据源都没有可确认内容，仍然生成完整正文：在“今日总览”明确写“在已成功读取的数据源中，未发现可确认的当日工作内容”，并在“来源引用与数据缺口”分别点名说明聊天、任务、日程的数据源读取结果。禁止留下空白正文。

若命令返回 `has_more` 但已达到官方分页上限或本次动作上限，不要猜测遗漏内容；在文档的“来源引用与数据缺口”中说明范围。

## 事实归并

按主题而不是逐条消息罗列。区分以下内容：

1. 今日总览
2. 重要沟通
3. 已确认决定
4. 已作承诺及截止时间
5. 已完成事项
6. 未完成、逾期和等待他人的事项
7. 日程与会议
8. 风险和阻塞
9. 明日优先事项
10. 待主体用户补充或确认
11. AI 后续建议（非已确认事实）
12. 来源引用与数据缺口

事实与建议必须分区，“AI 后续建议”标题和正文都要明确标注为非已确认事实。无法从日程或聊天核实会议结论时，只记录日程事实。不要把提议、问题、转述或未确认说法写成已确认决定。

保留必要来源标识：重要消息使用 `message_id`、会话名称和时间；任务使用 GUID 或 URL；日程使用事件 ID 和时间。不要把完整聊天正文复制到文档。

## 文档写入

创建或覆盖文档前，严格按官方 `lark-doc` Skill 阅读 XML、样式和 create/update workflow 说明。默认生成简洁 XML：

- 标题固定为 `YYYY-MM-DD <principal.name>每日工作记忆`，其中 `<principal.name>` 必须替换为配置中的主体用户名称；
- 新建使用 `docs +create --parent-token <folder_token>`；新建时必须在同一条 `docs +create` 命令中写入完整正文，禁止先创建只有标题的空文档再等待下一轮补写；
- 同日重跑使用 `docs +update --doc <token> --command overwrite`；
- 新建和覆盖更新的 `--content` 都必须以唯一的精确 `<title>YYYY-MM-DD <principal.name>每日工作记忆</title>` 作为第一个非空 XML 块，并将 `<principal.name>` 替换为配置中的主体用户名称，同时包含非空正文和“来源引用与数据缺口”；真实飞书会根据覆盖正文首块重新生成文档标题，因此 `docs +update --command overwrite` 也不得省略、后置或重复标题；来源说明必须分别覆盖聊天、任务和日程；只有标题或没有正文的内容禁止执行；
- 写入成功后使用 `docs +fetch --doc <刚写入的同一 token>` 读回验证；不得通过重新搜索后新建另一份来修复空文档；
- 不修改分享范围、权限或所有权；
- 不创建图表、画板、Base 或第二套工作流。

文档写入或写后读取验证失败时不要声称已生成。回复中说明失败环节和可执行的下一步。

## 输出约束

- 最终 JSON 的 `source_refs` 只使用当前触发事件及其已有上下文中的消息 ID；文档内可以引用读取结果中的真实来源 ID。
- 决策结果正文不添加 `🤖` 标签；本地系统事件不公开发言，普通飞书消息仍由可信运行时统一添加标签。
- 生成文档和读取飞书事实均使用主体用户身份；定时入口不借用 Bot 私聊触发，也不改变普通消息的收件身份路由。
