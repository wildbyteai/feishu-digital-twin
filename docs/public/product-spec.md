# 飞书数字分身完整公开产品规格

Status: implementation

## 目标

把现有飞书数字分身整理为可独立安装、配置、持续运行、升级、回退和卸载的完整开源产品。公开版本不得删减稳定能力，私有层只保留每个部署者自己的配置值、凭据、业务数据和运行状态。

首个稳定版本可以只支持 macOS。这是平台支持范围，不是功能分层。

## 产品组成

公开版本由同一版本的三部分组成：

1. **Codex 插件**：提供 Skills、安装、配置、诊断和控制入口；
2. **伴随运行时**：持续处理消息事件、主体用户身份补读、后台任务和可信边界；
3. **本机私有实例层**：保存部署者自己的非公开配置、凭据和运行状态，不包含私有功能代码。

飞书动作继续由官方 `lark-cli` 和 lark-* Skills 执行。模型推理继续通过 `codex exec --ephemeral` 完成，项目不开发模型供应商 SDK。

## 完整能力范围

稳定公开版本必须包含：

- Bot 官方实时事件和主体用户身份补充读取；
- 所有可见工作群与私聊的消息发现；
- 不强制 `@` 的语义触发和按需有界上下文；
- 发给谁由谁回复的固定身份路由；
- 自动消息统一 `🤖` 标识；
- Codex + Skills 驱动的忽略、回复、追问、确认和动作编排；
- 官方消息、任务、日历、文档、Base、Drive、Wiki 等能力；
- Base 控制台、自然语言规则、群级规则和知识空间配置；
- 企业知识库证据读取与每日工作记忆；
- 事件去重、补读游标、冻结、短期待确认和有限执行反馈；
- 后台连续运行、故障恢复、状态检查、升级、回退和卸载；
- 最小状态、日志脱敏、保留期和本地隐私清理。

实验性统计、远程遥测和共享多租户服务不因“完整版本”自动成为产品能力。

公共实例模板采用最小权限默认值，只启用消息域 `im`，并使用 `message_scope=bot_only`。其他飞书能力由部署者按需逐项开启并完成权限检查；完整版描述的是可安装能力集合，不代表默认授权集合。

消息发现范围是本机实例上限的一部分：

- `bot_only`：只处理 Bot 官方可见的实时消息，是所有新实例的默认值；
- `internal_visible`：补读主体用户可见的企业内部群聊和私聊，跳过外部群；
- `all_visible`：补读主体用户可见的全部群聊和私聊，包括外部群。

配置必须明确写出三档之一。首次选择 `internal_visible`、`all_visible`，或把已有实例扩大到更高范围时，安装/配置命令必须带 `--approve-message-scope`；缺少确认时在配置写入和服务启动前失败。该确认只用于实例范围授权，不是每条消息的审批；Base、AI、普通消息和后台任务都不能扩大范围。三档过滤、确认门、幂等 setup 和失败恢复已经实现，真实租户验收仍属于发布前独立复现。

## 三层数据边界

### 公开源码和发行包

- 插件 manifest、Skills 和控制命令；
- intake、runtime、executor 和 shared；
- 配置 Schema、状态迁移和后台服务模板；
- Base 控制机制、知识库和每日记忆实现；
- 合成 fixtures、测试、公共文档和发行工具。

公开仓不得依赖部署者私有仓中的功能脚本、迁移或诊断代码。

### 私有实例配置

- 主体用户显示名、称呼和时区；
- lark-cli profile 引用；
- Codex 环境引用、超时和最大反馈轮次；
- 启用的飞书能力域；
- 工作日、补读频率和每日任务时间；`schedule.workdays` 可选使用 ISO 1–7（周一至周日），省略时默认周一至周五；
- Base 控制台、知识空间和每日记忆目标引用；
- 自然语言授权规则和群级规则。

主体用户 `open_id`、控制 Base/表、明确配置的群级规则 chat ID、知识空间和每日记忆目标等跨重启稳定的资源标识属于本机私有实例配置。它们不得进入公共仓、发行包、普通日志或共享备份。

`🤖` 与 `【数字分身】`、`【建议】`、`【待<主体用户名称>确认】` 等模式标签由可信运行时统一生成，不能关闭或自定义。主体用户名称和称呼来自实例配置；待确认标签只从该名称派生，不新增独立文案配置。配置文件不得保存 API Key、OAuth Token、Cookie、二维码、消息正文或长期会话。

### 非 Git 本机私有运行态

- OAuth、API Key、Token、Cookie 和授权二维码；
- 运行中临时发现的 chat_id、thread_id、message_id、搜索结果和动作返回资源 token；
- Codex 内部端点、证书、认证状态和真实模型配置；
- 企业规则、知识映射、消息和文档正文；
- SQLite、`*.privacy-key` 本机 HMAC 密钥、日志、备份、缓存、每日工作记忆和验收证据。

本机私有目录使用 `0700`，敏感文件使用 `0600`，并按用途设置最短保留期。公共 JSON 示例和引导安装都默认采用 `message_scope=bot_only`、仅 `im` 域、7 天状态保留、3 天日志保留及 1 MiB/256 KiB 日志上限；公共 JSON 示例保持生产关闭，引导安装也只有在部署者显式确认生产数据、Doctor 与全部服务通过后才启用处理。Schema 的不可突破上限仍分别为 30 天、7 天和 10 MiB/1 MiB。`*.privacy-key` 与对应 SQLite 位于同一私有状态目录，只用于本机不可逆标识投影，不进入普通配置、备份共享或任何发行物。

## 配置层级与优先级

| 层级 | 放什么 | 能否扩大上一层权限 | 载体 |
| --- | --- | --- | --- |
| 可信代码硬门 | 回复身份、`🤖` 标识、所有权转让禁令、控制资源保护、去重、冻结和短期待确认 | 不适用 | 公开运行时代码与测试 |
| 本机实例上限 | 主体身份、`message_scope`、Codex CLI 运行环境、允许的飞书域、数据处理确认、调度和功能开关 | 否；这是实例最高权限边界 | Git 外 `0600` 配置；凭据继续由 Codex 与飞书官方工具管理 |
| 飞书 Base 控制台 | 总开关、允许域子集、自然语言运行规则、群级规则和知识空间路由 | 否；不能改变 `message_scope`，允许域只能收紧本机上限 | 部署者自己的两张 Base 表 |
| AI 业务判断 | 是否介入、回复内容、知识空间选择和授权内动作编排 | 否；只能在前三层允许范围内决策 | 通用 Skill + 自然语言规则 |

Base 配置采用统一短缓存刷新。每条消息在开始处理时取得一次快照，该消息的判断和执行始终使用同一快照；后续消息才会看到新配置。Base 不新增表、不编译规则，也不能增加本机未授权的飞书域。

Base 运行表必须包含“允许域”字段：值严格为“继承”时使用本机上限；有效非空列表取本机上限的子集；字段缺失、显式空值/空数组/空白、混合“继承”、未知域或任何超出本机上限的值都失败关闭。`control.mode=base` 时 Base 是个性化规则和群级规则的唯一来源；Base 个性化规则为空就表示当前使用空规则，不回退或继承本机规则。群级规则以 Base 中启用的记录为当前快照。自然语言规则可以改变业务处理方式，但不能越过可信代码硬门、`message_scope` 或允许域上限。

开源包只包含字段定义、安全默认值和中性示例，不包含任何部署者的配置值。个性化内容全部进入本机实例配置或 Base 自然语言规则，不通过修改源码形成私有功能分支。

## 不可配置关闭的可信规则

- 回复身份由消息来源固定；
- 自动消息必须明确标识为 AI；
- 所有权转让永久禁止自动执行；
- 去重、冻结、补读游标和短期待确认保持有效；
- Codex CLI 不可用或结构化输出不兼容时失败关闭；
- 日志不保存消息正文、模型输出或长期会话。

其他授权内事项由 AI 根据自然语言规则处理。确实缺少会改变承诺的关键事实时，AI 应直接在飞书发言中给出建议并请求主体用户确认，不建设第二套审批系统。

## 公共快照与发布

当前私有 Git 历史不得直接公开。公共源码从审核后的精确文件允许清单生成，不复制 `.git`、内部工作记录、本机运行态、私有 Overlay、日志、SQLite、`*.privacy-key`、二维码和真实验收证据。

公共快照在源文件、暂存树、解包归档和候选元数据阶段执行 Secret、PII、私有域名、本机路径和真实平台标识扫描。任何发现、来源缺失、脏文件或路径越界都必须失败关闭，且不能留下看似成功的候选。

CI 已使用只读默认权限和完整 commit SHA，运行格式检查、公共快照策略、通用 Secret/PII 扫描、完整合成测试、真实 npm package lifecycle 测试和 npm 文件清单；REUSE、CodeQL、Dependency Review、Dependabot 与 Scorecard 已配置为在公共仓启用。正式候选已生成确定性 SPDX 2.3、本地未签名 in-toto/SLSA 来源记录，并通过 REUSE、只读一致性校验、源码归档完整测试、Codex 官方插件隔离安装和 npm 离线安装闭环，确认三种发行物来自同一版本与同一允许文件集合。公开发布时仍必须在真实公共仓对最终产物生成 GitHub/Sigstore 签名 attestation。

最终候选必须在全新的非生产飞书租户中完成独立安装、完整能力、升级回退和卸载复现。公共仓、GitHub Release、Marketplace、npm 和公共目录均属于外部动作，必须在 Go/No-Go 后逐项取得明确授权再执行。

## 开箱即用验收

新部署者只需完成三个主步骤：

1. 接入飞书 CLI；
2. 启用 Codex；
3. 完成全局配置。

公开主入口为 `feishu-digital-twin setup --profile ... --timezone ... --codex-environment-root ... --approve-production-data`，普通用户无需预写 JSON，`lark-cli` 和 Codex 默认从 `PATH` 发现。省略 profile 时只读枚举：唯一 profile 自动选择，多个则要求明确指定。非 `bot_only` 或扩大已有消息范围时再追加 `--message-scope ... --approve-message-scope`；普通用户用 `--capabilities` 选择产品能力并生成最小业务域，高级用户才用 `--domains` 覆盖。选择企业知识或每日记忆但没有稳定资源引用时，setup 必须在任何写入前列出缺失资源、已有资源参数和 `--create-missing-resources`；部署者添加该开关后，setup 只编排官方 user 身份 CLI 的精确名称发现、`--dry-run`、创建和读回验证，不创建 Base/控制表或管理权限。高级用户仍可使用 `setup --config ...`，但不得与自动创建开关混用。安装器负责按需初始化、配置或安全更新，收口飞书 user/bot 授权验证、Codex 结构化输出、消息范围与数据边界确认、本机权限、后台服务安装和真实状态读回；所有步骤成功后才解除冻结。重复执行会收敛；本机失败恢复进入 setup 前的配置、冻结和服务状态，已成功创建的飞书资源保留并在重试时精确复用，不得静默开始真实回复或业务写入。

截至 2026 年 7 月 26 日，统一 `setup`、声明式配置、三档消息范围、控制 Base、知识与日报目标、缺资源结构化提示、官方 CLI 引导式创建、Doctor、服务管理、发行物构建、隐私扫描、SBOM、来源记录和公共仓均已实现。目标长期运行实例已完成版本切换后的 Doctor、后台服务、连续性、单应用单消费者和冻结/恢复验收；此前同一运行实现的 Bot/主体用户双身份回复和每日工作记忆真人证据保持有效。三档消息范围的真实租户独立复现仍按发布任务清单执行，不在此处提前声明完成。本次改动只增加 setup 的薄编排，不新增运行时业务代码：知识空间使用官方 `wiki +space-create`，日报目录使用官方 `drive +create-folder`，创建前 dry-run、创建后读回，ID/token 只进入本机私有配置。项目仍不建设第二套创建 API、工作流引擎、动作目录或长期聊天库。

## 不在范围内

- 直接公开现有私有 Git 历史；
- 公开真实实例配置、企业数据或本机运行态；
- 重建飞书 SDK、模型 SDK、动作目录或工作流引擎；
- 建设长期聊天库、公共消息中转或共享多租户 SaaS；
- 提前抽象 Slack、Teams 等尚未实际支持的平台；
- 为开源目的扩大飞书权限或修改生产业务规则。

## 完成标准

- 公共候选无法还原真实个人、租户、群、资源、业务正文或运行环境；
- 公开源码、插件包和 npm 包包含完整稳定功能且版本一致；
- 全部自动化测试只使用合成数据和 Fake 适配器；
- 干净环境可以完成真实飞书接入、后台运行、恢复、升级、回退和卸载；
- 用户可见 stdout/stderr、持久日志、SQLite、CI 日志和所有发行物通过隐私回归检查；内部消息 IPC 只能短期传递当前事件，不能落盘或回显；
- 不存在只保留在维护者私有层中的功能实现。
