# 完整开源方案

## 目标

把飞书数字分身作为一个完整、可自托管、可二次开发的 Codex 插件与伴随运行时公开。稳定功能全部采用 Apache-2.0 进入公共源码，不采用 Open Core；部署者只需提供自己的飞书授权、Codex 环境和实例配置。

最高原则保持不变：业务语义、智能触发、回复和动作编排由 Codex、项目 Skills 与自然语言配置完成；飞书能力优先复用官方 `lark-cli` 和 lark-* Skills；可信代码只保留官方组件无法代替的事件接线、身份路由、去重、冻结、游标、短期待确认和有上限的执行反馈。

## 推荐产品边界

采用“完整开源产品 + 私有实例”的单一版本，不采用 Open Core，也不为当前部署者保留私有功能代码。

| 应当公开 | 应当配置化但不公开配置值 | 应当始终留在飞书或本机私有环境 |
| --- | --- | --- |
| Codex 插件、通用 Skills、伴随运行时、安装/诊断/升级工具、Schema、服务模板、合成测试和公开文档 | 主体称呼、消息发现范围、允许域、调度、保留期、控制 Base、知识空间路由、每日记忆目标和自然语言规则 | OAuth、Token、Cookie、API Key、Codex 内部模型与端点、真实消息/文档正文、日志、SQLite、每日记忆和真实验收证据 |

开源项目只把 Codex CLI 当成黑盒推理入口。部署者使用官方登录、自建模型网关或第三方兼容 API，均由自己的 Codex 环境管理；本项目不读取、不识别也不保存模型供应商配置。

## 代码、配置与 AI 的分工

| 层级 | 负责内容 | 典型实现 |
| --- | --- | --- |
| 可信代码硬边界 | 身份路由、AI 标识、所有权转让禁令、消息范围上限、控制资源保护、去重、冻结、游标、短期待确认、保留期上限、执行轮次上限和失败关闭 | 少量可审计代码与强制测试，不能由 Base、Skill 或提示词关闭 |
| Git 外实例配置 | 主体身份、`message_scope`、允许域上限、Codex/lark-cli 环境引用、工作时间、调度、保留期和稳定资源引用 | `0600` 配置文件；禁止保存在产品源码树中 |
| 飞书 Base 控制台 | 日常启停、允许域子集、个性化规则、群级规则和知识空间路由 | 两张 Base 表，通过官方 lark-cli 读取；只能收紧本机上限 |
| Skill 与自然语言规则 | 介入判断、回复风格、知识检索顺序、确认话术、任务/日程建议、日报结构和企业业务差异 | 通用 Skill、可移植 README 式规则和 Base 文本，不为每家企业改代码 |
| AI 决策 | 当前消息是否需要回复、补读多少上下文、查询哪个知识空间、如何组合已授权动作 | Codex 临时决策；只能在前四层给出的边界内行动 |

判断原则很简单：需要确定性安全保证的才编码；能用官方 CLI/Skill 完成的绝不重建；企业语义和行为差异优先写规则；只有当前上下文才能决定的事情交给 AI。

## 隐私数据路径

每个任务都采用最小数据投影，不把整个实例配置和完整事件直接交给模型：

1. 官方事件或补读结果进入可信接线层；原始租户键、投递事件 ID 和路由用 `open_id` 只在可信层使用。
2. 可信层先完成身份、消息范围、内外部群、去重和排除规则判断。
3. 按意图生成最小 AI 输入：普通消息、知识检索和每日记忆分别使用字段白名单。
4. 每日记忆的排除群和排除主题必须在搜索结果进入 Codex 前由确定性代码删除；元数据不足以判断时失败关闭并记录数据缺口，不能把判断交给 AI。
5. Codex 只接收当前事件、必要的同群有界上下文、当前群规则和完成任务所需的资源引用；日报目录和排除表不进入普通消息提示词。
6. 执行继续通过官方 lark-cli 和 lark-* Skills；反馈只保留下一轮决策需要的结构化结果，并受字节数和轮次上限约束。
7. 不建设长期聊天库。持久状态仅保存去重、游标、冻结、短期待确认和不可逆标识投影；日志不保存正文、完整模型输出或原始飞书标识。

## 配置模型收口

运行开关只保留一种权威来源，避免本机开关与 Base 开关相互矛盾：

- `control.mode=base` 时，Base 是唯一日常启停来源；本机仍只保存不可突破的消息范围、允许域和数据处理许可。
- `control.mode=local` 时，不配置控制 Base，由本机开关负责启停。
- 两种模式必须二选一，`status` 和运行时读取同一有效值；Base 永远不能改变 `message_scope`、扩大允许域或修改可信硬边界。

配置分为两个阶段：候选配置可以使用便于安装器解析的引用；安装完成后的活动配置必须使用绝对、Git 外、权限正确的本机路径。`setup`、`configure` 和 `config update` 必须共用同一套路径安全检查，拒绝源码树内配置和通过符号链接逃逸的路径。

知识空间路由只保留一种表达：继续使用 Base/实例中的自然语言 `authority_rules`，由 AI 选择空间；不再同时维护另一套代码化路由表。公共示例只给中性写法，不包含真实空间 ID、表名或业务词。

## 发布前必须完成的隐私硬门

按优先级处理，不增加新的业务框架：

1. **P0 已完成：日报排除真正生效。** 官方消息搜索结果进入下一轮 Codex 前按排除群和明确 topic/thread 元数据过滤；元数据不足时删除正文并返回脱敏缺口，失败关闭测试已覆盖。
2. **P0 已完成：提示词最小化。** 普通消息不再携带真实主体 `open_id`、租户键、投递 ID、日报 folder token 和全部排除表；普通消息与日报均已有字段白名单和 canary 测试。
3. **P1 已完成：公开候选私有词表自动覆盖。** 正式构建可从源码树外 `0600` 活动实例配置在内存中派生 profile、实例 ID、主体名称与别名、Base/表、文件夹、群，以及规则中明确标注的公司、组织、品牌、项目、知识空间、资源引用和租户域名，并与维护者私有策略合并；明确标注的短身份值也会进入禁词。普通布尔、数字和未标注的通用短词不会成为禁词，配置路径与派生值不写入候选、receipt 或输出。无法从结构化字段和明确规则引用中可靠推断的企业业务词继续由私有策略补充。
4. **P1 已完成：配置路径与开关语义统一。** `setup`、`configure` 和 `config update` 共用源码树外、符号链接和权限边界；Schema v2 使用单一 `control.mode=local|base` 权威开关，`status` 与运行时读取同一有效值，v1 仅保留只读兼容。
5. **P1 已完成：向导补齐现有资源配置。** 普通 setup 已覆盖已有控制 Base、知识空间、每日记忆目标和主体别名，自动保留资源所需官方域，并通过官方 CLI 只读校验 Base 必要字段、Wiki 名称/`space_id` 和 Drive 文件夹；参数缺项、多规则源和断权配置都会失败关闭。工作时间、调度和保留期继续使用安全默认，高级 JSON 仍保留。新资源创建是独立飞书写操作，继续使用官方 CLI dry-run 与部署者明确批准，不在 setup 中重建工作流。
6. **P2 已完成：Schema 与 Loader 收口。** 能力目录、官方业务域白名单、`auth/api/event/profile` 等保留域拒绝、活动路径绝对化、v2 单一控制源、Base 空规则语义和全部配置更新入口的统一契约已经落地。逐能力精确 scope 属于真实授权验收，不再挂在 Schema 实现项下。

这些硬门完成后，隐私边界由代码和测试保证；个性化仍由配置、Base、Skill 和 AI 完成，不需要继续扩大自研运行时。

## 公开、私有和配置三条边界

| 分类 | 内容 | 存放位置 | 是否进入公开发行物 |
| --- | --- | --- | --- |
| 完整公共产品 | Codex 插件、项目 Skills、伴随运行时、配置 Schema、安装/诊断/升级工具、服务模板、合成测试、文档 | 公共仓与同版本发行包 | 是 |
| 实例配置 | 主体称呼、时区、工作日、消息范围、能力域、控制 Base、知识空间、每日记忆目标、自然语言规则 | Git 外 `0600` 本机配置；可配置项也可由部署者自己的 Base 控制台收紧 | 否 |
| 凭据与认证 | 飞书 OAuth/Token/Keychain、Codex 登录态、API Key、模型端点 | 官方 CLI、Codex 或部署者批准的秘密环境 | 否，项目也不读取明文 |
| 私有运行态 | 去重状态、补读游标、短期待确认、脱敏结果日志、每日工作记忆 | Git 外 `0700` 本机目录，按保留期自动清理 | 否 |
| 企业数据 | 消息、文档、知识库、任务、日程和 Base 正文 | 飞书与处理当下的有界上下文 | 否，不建设公共中转或长期聊天库 |

当前私有 Git 历史包含内部工作记录和真实验收痕迹，不能直接改成公共仓。首次公开必须从审核后的精确文件允许清单创建一个全新仓库和全新初始提交；`.git`、内部工作记录、本机运行态和历史删除对象都不得复制。

## 配置化设计

### 部署时配置

- 主体显示名、称呼、时区和工作日；
- `lark-cli` profile 引用、Codex CLI 路径和隔离环境引用；
- `bot_only`、`internal_visible`、`all_visible` 三档消息发现范围；
- 允许使用的飞书能力域及生产数据确认；
- 工作时间/非工作时间补读频率和每日记忆时间；
- 控制 Base、知识空间、每日记忆目录等稳定资源引用。

### 飞书 Base 控制台配置

- 总开关和能力域子集；
- 自然语言业务规则；
- 群级特殊规则；
- 知识空间路由；
- 可以收紧但不能扩大本机配置确定的消息范围和权限上限。

### Skill 配置

可移植的业务差异优先写成 Skill 和自然语言规则，例如介入判断、回复风格、知识检索顺序、确认话术、任务/日程建议和每日总结结构。只有需要确定性安全保证的部分才写入可信代码。

### 不允许配置关闭的规则

- 发给哪个身份的消息由哪个身份回复；
- 自动发言必须带 `🤖` 和数字分身身份说明；
- 所有权转让永远不能自动执行；
- 去重、冻结、补读游标、短期待确认和保留期继续有效；
- Codex 或官方飞书能力不可用时失败关闭；
- 日志不得保存消息正文、模型完整输出、凭据、原始飞书 ID 或长期会话。

## 隐私收束

1. **默认最小范围**：公共 JSON 示例保持 `control.mode=local` 且 `enabled=false`；引导安装只有在部署者显式确认生产数据并通过全部检查后才启用处理。两条路径都默认使用 `message_scope=bot_only` 和仅 `im` 域；扩大消息范围或能力域必须由部署者明确配置。
2. **本机处理**：默认无遥测、无公共消息中转、无自动调试包上传；Codex 使用什么模型服务由部署者自己的 Codex 配置决定。
3. **短期状态**：只保存去重、游标、冻结和待确认所需的最小状态；不保存长期聊天正文。日志只输出随机追踪号、阶段码、数量、耗时、脱敏错误分类，以及由本机隐私密钥生成、受保留期限制的类型化 HMAC `execution_hash`；该指纹只用于重复执行审计，日志继续禁止 `command_hash`、命令参数和正文。
4. **标识投影**：日志或统计需要稳定关联时使用本机 HMAC 投影，不输出原始用户、群、消息和资源标识；`*.privacy-key` 永不进入备份或发行物。
5. **公开内容扫描**：CI 对公共允许清单中的每个文件执行通用 Secret、PII、私有域名、本机路径和飞书资源标识扫描，只输出 finding code 与相对路径。正式候选额外读取源码树外 `0600` 活动实例配置，在内存中派生稳定私有标识并与维护者私有词表合并；配置路径、配置值和派生禁词都不进入候选、输出或 receipt。
6. **公开协作收束**：Issue/PR 模板禁止粘贴真实消息、企业数据、凭据、飞书 ID、原始日志和截图；安全问题只通过私密漏洞渠道处理。

## 公共产品形态

同一版本生成三种完整候选：

- 源码归档：适合审计和二次开发；
- Codex 插件包：包含项目 Skills、插件清单和所需伴随运行时；
- npm 包：提供安装、配置、诊断、后台服务和运行入口。

三种候选必须来自同一个审核后允许清单、同一个版本和同一个源码提交。Node.js、Codex CLI、官方 `lark-cli` 和官方 lark-* Skills 由部署者单独安装和授权，不复制进发行包；项目不关注 Codex 内部使用官方模型、自定义模型还是企业网关。

## 公共仓门禁

- 所有第三方 GitHub Actions 固定到完整 40 位 commit SHA；
- 默认 `GITHUB_TOKEN` 只读，不使用 `pull_request_target`，不向不可信 PR 提供秘密；
- macOS 运行完整合成测试、公共策略检查、公共内容扫描和 npm 文件白名单检查；
- REUSE/SPDX 自动检查 Apache-2.0 声明；
- CodeQL、Dependency Review、Dependabot 和 OpenSSF Scorecard 只在公共仓启用；
- 公共候选只携带 CODEOWNERS 示例；创建公共仓时必须写入真实维护团队，之后强制隐私、发布、身份边界和可信执行代码由维护者评审；
- 候选 SBOM、来源证明和消费者侧校验在本地正式候选阶段完成；真实分支保护与公共发布签名在创建公共仓后启用并纳入 Go/No-Go。

## 首次公开流程

1. 在当前私有仓完成代码审查、完整测试和公共允许清单扫描。
2. 用源码树外活动实例配置派生禁词并合并维护者私有策略，构建脱敏候选，验证源码、插件和 npm 三种产物内容一致；该步骤已在 `0.1.0` 正式候选完成。
3. 在全新非生产飞书租户完成安装、消息双入口、知识库、授权动作、每日记忆、升级、回退和卸载验收。
4. 从候选快照创建全新公共仓和单一初始提交；不得推送当前私有仓历史。
5. 配置真实 CODEOWNERS 团队、安全报告地址、分支保护、发行身份和发布凭据。
6. 校验候选自带的确定性 SPDX 与本地来源记录，并在公共仓对同一最终产物追加 GitHub/Sigstore 签名 attestation；正式候选的归档解包、npm 安装和插件安装闭环已完成，公共签名与公开来源读回仍待执行。
7. 逐项取得明确授权后再创建公共仓、推送、发布 GitHub Release、Marketplace、npm 和公共目录；任何一步失败都不影响当前本机服务。
